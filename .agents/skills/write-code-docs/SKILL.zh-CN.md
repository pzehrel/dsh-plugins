# 编写代码文档

## 用途

使用本技能以仓库选定的语言准确记录行为、契约、工作流和运行约束，并覆盖私有代码，以及原因无法从代码看出的实现代码块。

## 适用时机

当编码任务新增或改变行为、公共或消费者可见声明、不显然的实现代码块、源代码/配置/schema 文件，或面向人的 Markdown/API 文档时，主动应用本 skill——即使请求没有写“docs”或“comment”。不要等这些词出现。

理解代码变更后，为受影响的公共和私有符号，以及原因无法从代码看出的实现代码块添加文档。对于目的和影响已经显然的简单变更，
不要仅因为选中了本 skill 就添加说明。

## 语言策略

生效的 `AGENTS.md` 是自然语言与双语模式的唯一权威，并可分别设定代码注释/docstring 与 Markdown/API 文档。写作前先读取它。

- 当前文档载体对应的规则明确要求双语时，使用英语加且仅加一种本地化语言。
- 该规则未说明时，只写一种语言，遵循相邻文件或仓库约定。
- 不要因为用户语言、存在本地化文件或本 skill 自身的翻译文件就推断需要双语。
- 本地化语言从仓库说明、已有对应文件、本地化配置和用户请求中确定。不要假定中文、用户语言或其他默认值；证据不足以确定时，先询问再动笔。
- 启用双语模式时，英语位于前面；本地化块必须是完整、忠实的翻译，保留声明、语气、条件、示例和强调；只有在不改变技术含义时才可使用自然语法。

两类文档载体保持区别：

- **代码注释与 docstring：**单语模式下，在选定语言中使用一段完整内容。双语模式下，在同一处注释/docstring 内先放完整英语块、空一行，再放完整本地化译文。不要把双语文本拆到相邻注释块中。
- **Markdown 文档：**每个独立页面保持独立；单语模式下使用选定语言的一份文件；双语模式下使用英语和本地化两份完整成对文件，例如 `README.md` 和 `README.zh-CN.md`。不要在一个文件中逐段交替语言或重复表格/代码块，除非明确要求。

## 工作流程

1. **确定语言设置。**读取生效的 `AGENTS.md`（通常已在 Agent 上下文中），并按「语言策略」一节执行，对代码注释/docstring 与 Markdown/API 文档分别应用。
2. **写作前检查。**阅读面向相同读者、具有相同目的的最近文档；确定发生变化的行为或流程、权威来源（代码、类型、测试、配置或命令输出）、目标读者，以及应修改的最小文档表面；把每个目标分类为代码内注释/docstring 或独立 Markdown 文档。
3. **阅读与当前工作匹配的文件。**处理代码时，先读 [code-comments.zh-CN.md](references/code-comments.zh-CN.md)，再根据注释语法只读一个示例文件：TypeScript/JavaScript/Java 使用[块文档注释（`/** ... */`）](references/comment-syntax-block.zh-CN.md)，Rust 使用 [Rustdoc（`//!`/`///`）](references/comment-syntax-rustdoc.zh-CN.md)，Python 使用 [docstring/注释](references/comment-syntax-python.zh-CN.md)，HTML/XML 使用[标记注释（`<!-- ... -->`）](references/comment-syntax-markup.zh-CN.md)。仅处理 Markdown/API 时读 [markdown-docs.zh-CN.md](references/markdown-docs.zh-CN.md)。如果改动新增或修改了命令行开关、环境变量、配置键或错误码，还要更新列出它们的 Markdown 文档表面，因此即使主要工作是代码，也要为这部分阅读 `markdown-docs.zh-CN.md`。混合语言文件逐个读取对应的示例文件。
4. **边写边改。**在同一次修改中实现或编辑并补齐文档，不要推迟到单独的阶段。满足你所触及载体的最小交付：代码看 [code-comments.zh-CN.md](references/code-comments.zh-CN.md)，Markdown/API 文档看 [markdown-docs.zh-CN.md](references/markdown-docs.zh-CN.md)。同时检查已有名称、链接、术语、示例、版本范围和废弃策略，保留无关修改，不要在互相竞争的权威位置重复同一契约。
5. **验证结果。**运行适用的测试、类型检查、文档 lint、链接检查和示例验证。没有自动检查时，针对权威来源通读结果；当呈现可能隐藏含义时，检查渲染后的 Markdown。确认声明、链接、示例以及 API/成员覆盖都有依据；仅对 `AGENTS.md` 启用双语的文档载体执行双语对等检查。

然后用一两行报告覆盖情况——记录了哪些、有意跳过了哪些及原因——让审查者看到覆盖决策，而不是自己去发现遗漏。

当权威行为、目标读者、语言策略或文档范围存在重大歧义时停下并询问。保持请求边界明确，不要添加无关工作。

## 示例

示例：记录新的错误场景时，使用选定语言更新 API 文本（仅在启用双语模式时再更新本地化对应文本），加入触发条件和恢复示例，并确认实现确实会产生该错误。

示例：当私有辅助函数包含带上限的重试循环和清理逻辑时，记录重试上限、退避、清理顺序，以及这些选择保护周围状态的原因。
即使辅助函数的名称和签名清晰，也要在循环或辅助函数旁边添加注释。

## 前置条件

- 能够支持每条声明的实现、配置、测试或现有文档事实来源。
- 在可用时运行文档、链接、格式或渲染检查。

## 限制

- 文档工作不得修改 API、发布产物或添加无关指令。
- 不得把本 skill 当作 API 设计指南；它记录已经存在的行为。
- 不得编造缺乏事实来源支持的行为、契约、示例或翻译。
- 不得在普通参考 Markdown 中要求消费端 Agent 忽略仓库规则或编辑文件。

## 故障排查

- 语言策略或本地化语言不明确：按「语言策略」一节处理；若证据仍不足以确定必需的本地化语言，先询问再动笔。
- 双语文件不一致：逐项对照声明、语气、示例、标识符和顺序；仅在启用双语模式时执行此项检查。
- 链接或示例失败：从仓库根目录解析，并对照当前实现验证。

## 文档标准

让文档解释读者真正需要依赖的行为。文档应靠近事实来源，完整到足以供开发者或编码 Agent 使用，
同时保持可维护的简洁。当文档描述公共行为、支持的工作流或运行约束时，它就是接口的一部分；不要
把代码尚未实现的行为写进文档。

在编写代码注释、docstring、JSDoc/TSDoc、API reference、`AGENTS.md` 及其他 Agent 指令文件、README、指南、示例、
变更日志和其他 Markdown 文档时使用本 skill。

每个独立 Markdown 页面都应可单独阅读，并能从相关索引、指南或上级文档到达；不能留下没有任何入链的文档。
