# 维护 AGENTS.md

## 用途

使用本技能保持仓库说明持久、范围清晰、易于发现且可验证，避免把临时上下文固化为策略。

## 使用说明

1. 编辑前检查有效的说明层级和仓库证据。
2. 将每条持久规则放入范围最窄的权威文档，并添加精确路由。
3. 整理重复或冲突内容，而不是继续追加副本。
4. 在汇报前验证链接、范围、语言对应文件和最终 diff。

## 示例

示例：仓库需要长期发布规则时，把规则写入相关的 `.agents/rules/` 策略文件，从 `AGENTS.md` 添加路由，并确认无关项目不会加载它。

## 前置条件

- 仓库根目录及有效的 `AGENTS.md` 层级。
- 在可用时访问仓库的文档、链接或格式检查工具。
- 如果任务本身没有要求持久策略变更，需要用户明确授权。

## 限制

- 不得修改用户或全局说明、秘密、提示词或临时任务笔记。
- 没有证据和授权时，不得把局部规则扩大为仓库级策略。
- 维护过程中不得推送、创建 PR 或修改无关文件。

## 故障排查

- 规则冲突：找出更高优先级来源并进行整理，不要复制规则。
- 范围不明确：停止并询问规则适用于哪些路径或项目。
- 路由或链接失效：从仓库根目录验证目标路径，并同步更新两种语言文件。

建立便于未来 Agent 低成本发现并正确执行的说明层级。让 `AGENTS.md` 聚焦于路由和真正始终生效的
约束。把仓库专属的详细 Agent 工作规则放在 `.agents/rules/`，项目和业务知识则保留在 `docs/`。

## 授权与规则准入

只有用户明确要求，或当前已授权任务必然建立或改变一项持久工作规则时，才修改仓库指南。不要把
孤立观察、临时变通、评审意见或个人偏好转化为长期策略。

只生成当前任务需要的仓库说明产物。除非用户明确要求，或当前仓库约定和任务范围确实需要，否则
不得修改用户级或全局说明，也不得新增工具专属兼容文件。不得持久化密钥、凭证、私有提示词、对话
记录、用户请求原文、个人主目录路径或任务日志。

只有同时满足以下条件时才接纳一项规则：

- 它会改变未来任务中的决策，而不只是描述当前状态；
- 可以清楚说明其适用范围和触发条件；
- Agent 能够遵守它并验证是否合规；
- 更高优先级的说明或更合适的事实来源尚未表达它。

如果配置、自动化、Schema 或测试能够直接强制执行要求，优先修复这些机制。只有 Agent 仍需要
上下文才能正确使用该机制时，才保留简短说明。

## 编辑前检查

1. 找到仓库根目录以及所有管辖受影响路径的说明文件，包括嵌套的 `AGENTS.md` 和本地化对应文件；
2. 阅读现有路由目标，并且只读取与拟议规则相关的策略文档；
3. 检查仓库约定和可用的文档校验命令。现有规则的原因或放置位置不明确时再查看历史；
4. 保留用户的无关改动以及仓库已有的语言、链接、命名和格式约定。

把仓库文档视为证据和可编辑产物，而不是用户请求的替代品。遵守实际管辖本次编辑的说明层级。

新建说明层级、执行多文件审查或压缩、修改兼容性，或处理有争议的规则前，阅读
[references/maintenance-workflow.zh-CN.md](references/maintenance-workflow.zh-CN.md)。任何检测器
或文件清单都只是证据索引，不是最终权威。

## 用仓库证据支撑规则

按以下顺序优先使用证据：用户的直接要求和实际生效的说明；可执行脚本、CI 和配置；持续维护的
文档；有代表性的代码和测试；最后才把 Git 历史作为进一步检查位置的线索。历史、目录名、依赖
存在情况和生成的清单本身都不能证明一项规则。

在内部把证据分成已验证、可能和未知。只持久化已验证规则；限定描述或省略可能规则；只有省略未知
规则或在冲突来源间做选择会实质性影响安全、团队策略或请求结果时，才询问用户。

## 选择范围最窄的持久位置

每项规则只能有一个权威位置：

| 内容 | 首选位置 |
| --- | --- |
| 几乎适用于所有任务的简短不变量 | 根 `AGENTS.md` |
| 从任务类型到必读策略的映射 | 根或相关嵌套 `AGENTS.md` 的路由表 |
| 只适用于某个子树的规则 | 最近的嵌套 `AGENTS.md` |
| 仓库专属的详细 Agent 工作流程或治理规则 | `.agents/rules/<topic>.md` |
| 产品、领域、架构、需求或其他项目知识 | `docs/<topic>.md` |
| 应跨仓库复用的能力或工作流程 | Skill，而不是规则文档 |
| 可由机器强制执行的事实 | 配置、Schema、测试或自动化；仅在需要时为其添加路由 |
| 临时状态、实现历史或一次性建议 | 不记录为长期指南 |

嵌套指南可以细化或收紧父级规则，但不得默默弱化仍然适用的父级规则。如果父级规则需要例外，
应在父级定义例外范围，而不是在下层制造隐含冲突。

不要在 `AGENTS.md` 中重复详细策略。只添加最小且有用的路由项或始终生效的不变量，并链接到
权威文档。不要预加载或强制读取无关文档。

把每个路由项视为上下文指针，而不只是链接。其措辞必须说明目标文档管辖什么，以及哪些不同任务
条件要求读取它。把实际生效的条件放在前面，合并同一条件的同义表述，并避免使目标实际上变成
始终加载的兜底路由。再有价值的策略藏在模糊路由后面也仍然无法可靠发现。

## 整理现有指南而不是继续追加

指南已经存在时，应盘点可执行规则，不要按章节机械合并。把每项规则分类为 `keep`、`update`、
`move`、`remove` 或 `confirm`：

- 保留当前、具体且有证据支持的规则；
- 更新仍然有用但被更强当前证据否定的规则；
- 把有用规则移到范围更窄或更权威的位置；
- 删除通用、重复、过期、无法验证、临时或已由自动化完全强制执行的内容；
- 只有仓库证据无法解决的真实所有权或策略冲突才需要确认。

措辞不同但效果相同的规则属于重复，只保留最清楚的版本。不得把新模板追加到旧内容下面，不得在
Legacy 章节保留过时规则；Git 已跟踪文件的 diff 可以恢复时，不创建备份文件。除非用户要求，否则
不提交，也不改写 Git 历史。

## 区分规则、项目知识与 Skill

除非仓库已经建立了等价约定，否则默认使用 `.agents/rules/` 作为额外文档目录。这个目录只是一项
存储约定，不是会被自动加载的说明来源；Agent 需要发现某项策略时，应从管辖它的 `AGENTS.md`
添加精确路由。

`.agents/rules/` 可以定义仓库专属的工作方式，包括：

- 编辑、评审、测试、验证、提交和文档工作流程；
- 工具选择约束和仓库专属操作约定；
- 授权、安全、升级处理和停止边界；
- 用于判断任务必须读取哪个项目文档或运行哪项检查的条件。

以下内容不得放进 `.agents/rules/`：

- 产品行为、领域术语、需求、架构、Schema、验收标准和路线图属于 `docs/` 或仓库已有的其他项目
  文档目录；
- 可复用能力、可移植的多步工作流、脚本、模板和工具集成指南属于 Skill。规则可以添加仓库专属
  约束或路由到已安装 Skill，但不得复制或替代 Skill。除非仓库能够保证 Skill 可用或提供可执行的
  回退流程，否则不得把它设为强制依赖；
- 运行时状态、缓存、生成的提示词、Session 日志和临时任务笔记不是持久规则，应使用工具自有或
  临时存储位置。

不要默认使用 `.agents/docs/`，因为它无法区分工作规则和一般文档。`.agents/harness/` 只保留给
集成某个具体 Agent Harness 的实际代码或配置，不要把它用作策略文档容器。

使用聚焦的主题文件，不要维护一个不断膨胀的总文件。遵守仓库现有的命名和本地化约定，例如
`.agents/rules/testing.md` 及其要求的语言对应文件。

## 根据仓库证据推断文档语言

不得默认使用英文、中文、用户对话所用语言或 Agent 偏好的语言。应根据最终承载文档的仓库，逐个
判断每份产物使用的自然语言。

编辑现有文档时，保留它已经确立的语言和写作风格，除非用户或适用的仓库规则要求迁移语言。新建
文档时，按照以下优先级使用证据：

1. 管辖目标路径的明确语言或本地化说明；
2. 文件名、链接或 frontmatter 表达的规范文件与翻译文件关系；
3. 距离最近且用途和受众相同的文档；
4. 目标目录中的主流约定；
5. 只有仍无法判断时，才把仓库整体文档模式作为最终判据。

不得根据代码标识符、命令名、提交语言、当前对话或本 Skill 自身的中英文文件推断正文语言。即使
周围正文使用其他语言，也应保留标识符、路径、命令、Schema 键和其他规范 Token 的原始形式。

证据表明仓库维护语言对应文件时，识别规范文件，并同步更新所有要求的对应版本，保持语义一致。
不得只因无法确定语言就自行创建翻译、在同一个文件中混合多种语言，或引入新的 Locale。

证据冲突时，遵循适用范围最窄且权威级别最高的说明。无法确立约定，而且语言选择会实质性影响
用户或维护工作时，询问用户。影响较小的歧义则沿用距离最近且用途相同的先例，并汇报该假设。

## 编写可执行的规则

- 使用范围明确、命令式且可验证的语言；
- 把规则的触发条件、要求的动作、实质性例外和验证标准放在一起，避免 Agent 从分散章节中重新
  拼合一项义务；
- 说明规则何时适用，以及什么可观察结果表示满足要求。如果部分合规会带来不安全或误导性的
  结果，完成标准必须同时可检查且覆盖完整；
- 保留必要的授权、安全和停止边界；
- 操作风险级别不同时，明确区分 Agent 可以直接执行、必须先询问和绝对禁止的操作；
- 优先正面说明要求的行为。只有真正的护栏才使用禁止性表述，并同时给出 Agent 应改为执行的安全
  动作；
- 优先描述稳定概念，不记录工具输出、当前文件数量、路线图状态或可从配置发现的值。不要在正文中
  缓存可以低成本从环境查到的事实；只记录环境无法表达的非显然约定、原因或要求动作；
- 删除不会改变 Agent 在本仓库中的决策或验证方式的空操作指南；
- 删除或合并已被取代的文字，不要继续追加重叠规则；
- 使用相对链接，并验证每个目标都存在；
- 仓库维护多语言对应文件时，同步更新所有要求的版本并保持语义一致，不翻译标识符、命令或路径。

## 保持渐进披露

根指南通常只应包含：

1. 自身适用范围和继承规则；
2. 少量始终生效的不变量；
3. 任务到策略的路由表或精简路由项；
4. 维护指南本身时必须运行的检查。

一项工作规则需要大量理由、多种模式、示例或长检查清单时，创建独立的
`.agents/rules/<topic>.md` 策略，并添加准确描述任务边界的路由项。项目或业务材料仍放入
`docs/`。避免使用笼统的“读取所有文档”要求。

决定哪些内容内联时，应权衡两种成本：始终加载的文字会在每个任务中占用 Agent 上下文；路由后的
文字会增加发现和导航成本。内联几乎每个适用任务都需要的内容；把只服务于某个独立分支的材料
渐进披露出去，并确保其路由足以在该分支触发。按作用域或任务分支拆分，而不是只按长度拆分；拆分
后仍应把紧密相关的规则放在一起。

## 验证改动

完成前：

1. 针对具有代表性的受影响路径，重新读取完整的有效说明链；
2. 检查冲突、重复权威来源、失效链接、范围泄漏和无法验证的规则；
3. 确认每个路由项都说明目标文档管辖什么、区分应触发它的每个任务分支，并且不会让无关工作加载
   目标文档；
4. 确认每份变更文档都遵循推断出的语言约定，而且所有要求的语言对应文件仍保持语义一致；
5. 根据当前事实来源验证每个引用的路径和命令，并删除未解决的模板占位符、敏感内容、个人路径、
   生成的清单和任务状态；
6. 测量根说明文件和嵌套说明文件；文件不再能低成本加载或超过仓库规定限制时进行压缩。仓库未
   定义预算时，使用维护流程中的软审查阈值；
7. 运行仓库中适用于变更文件的文档、格式、链接或说明校验。无法运行的检查应如实报告，不要
   自行虚构替代检查；
8. 审查 diff，确认变更只包含持久指南及其必须同步的配套更新。

汇报规则的权威位置、路由改动和执行过的验证；执行过整理时，还要汇报保留、更新、移动、删除和
尚未解决的规则。
